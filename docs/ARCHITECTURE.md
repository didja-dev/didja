# Architecture

## Pipeline

1. **Capture** (Swift, native, per OS) — our own layer, no third-party recorder.
   - **Triggers:** frontmost-app change (NSWorkspace), AXObserver on the focused window (focus, title, value changed), plus a 5s poll; 1s debounce. Only the focused window is ever read.
   - **Primary source, Accessibility API:** walk the focused window's AX tree (depth and char caps), collect AXStaticText / AXTextArea / AXTextField values, the window title, and AXURL of web areas. Chromium and Electron apps (Chrome, Claude desktop, Slack, VS Code) need AXManualAccessibility / AXEnhancedUserInterface set to true before their tree fills in.
   - **Fallback, OCR:** when AX returns too little text, grab one frame of that window with ScreenCaptureKit (SCScreenshotManager), run Vision VNRecognizeTextRequest, drop the image. The frame is of the focused window only: the on-screen window with its title, or the app's only window. When neither fits, nothing is read. That window's own title must also pass the exclude list (`OCRCapture.pick`). It runs only when `OCRCapture.shouldRun` says so: Screen Recording granted, the `ocrFallbackEnabled` switch on (Settings › General, on by default, SCR-41), fewer than 40 characters from AX, and at least 10 s since the last frame. This is the only use of ScreenCaptureKit, and it is what macOS's periodic "bypass the system private window picker" alert is about.
   - **Diff:** hash per window; store only lines new since that window's last snapshot (a line is the same line only under the same section and as the same occurrence, so a second "Done" or a re-run command is new), as an observation (ts, bundle_id, app, window_title, url, source ax|ocr, text).
   - **Privacy:** bundle-ID denylist (password managers, Keychain Access, user-added banking apps), skip AXSecureTextField and private/incognito windows, pause hotkey + menu toggle, 24h TTL.
   - **Permissions:** Accessibility (required); Screen Recording (only for the OCR fallback). Onboarding explains both.
2. **Extract** — every ~60s, new observations are scanned for task-like content: numbered checklists in Claude / Claude Code, "don't forget / please reply" in email, setup steps in docs. Heuristics first, on-device model second, Claude API on escalation. Each task stores: title, source app/URL, done-criteria, markers.
3. **Match completion** — three tiers:
   - **Exact markers:** env var names, URLs, email subjects, file names → text search on new observations.
   - **Context:** marker must appear in the right app/URL (Vercel prod env page, not the editor).
   - **Model judgement:** for fuzzy tasks, compare recent observations to done-criteria; low confidence → "Looks done — confirm?" instead of a silent tick.
4. **UI** — menu bar list: open items grouped by source, tick/snooze/dismiss, evidence link ("why I think this is done"), nudge when an item from an abandoned checklist sits >N hours.

## Data

SQLite, schema in [`schema/001_init.sql`](../schema/001_init.sql):

- `observations(id, ts, bundle_id, app, window_title, url, source, text)`
- `tasks(id, title, source, criteria, markers, status, confidence)`
- `evidence(task_id, observation_id, ts)`
- `sources(id, kind, ref)`

Each task also keeps where it was captured (`place_bundle_id`, `place_app`, `place_window`, `place_url`, schema 14). "Go to Source" asks the engine for it (`didja place <id>`), then `SourceJumper` raises that window, reads it again and scrolls the best-matching line into view (`AXScrollToVisible`). Nothing it reads is stored.

When the line is not in any window, an app with a sidebar of conversations (Claude) has the conversation opened by its name: a link is followed, a row or cell selected, and no other button is pressed than a sidebar entry whose whole text is exactly the conversation's name, or the name and at most three status words ("Running", "2m", "5h ago"; `isNameWithStatus`), in the left third of the window, as Claude shows conversations (`sidebarStep`, `mayPressConversationButton`). `Didja --go-to-source <place.json> --look-only` reports what it would press, without touching anything. If the line is further up than the app has loaded, `pageUpThroughConversation` brings the top message (the first sentence-long text outside the sidebar's column) into view and turns the scroll wheel over the conversation, from a private event source, without moving the pointer. Everything that scrolls asks `Watch` first: it stops after 5 seconds of scrolling (10 in all, with the wait for a page to load), or as soon as the pointer moves, a key, click or scroll of yours arrives, or another app comes to the front (`stopReason`).

Capture writes observations; the engine reads them and writes tasks. Windows later = UI Automation + Windows.Media.Ocr writing the same observations table, engine unchanged.

## Hard rules

- No Screenpipe or any other third-party screen recorder. Capture is ours, built only on Apple APIs.
- Never store screenshots or video. OCR frames are processed in memory and dropped.
- Store text only, deduped per window. Observations auto-expire after 24h.
- How a task looked (SCR-31, schema 016 `task_context`): when a task is created from an observation, the engine keeps its line and up to three non-empty lines on each side (`context.ts`, `contextLines`; capture markers left out, each line cut to 240 characters), with the window's app, title and URL. Nothing is kept when the task's words are not found there. `pruneContext` deletes the rows of done and dismissed tasks on every poll; the app deletes them all with Forget Captured Text Now and those of an excluded window with the observations (`ObservationStore`). CLI `context <id>`; a checklist shows its first step's. The app shows it under the row (`SourcePreview`, the row's button or V).
- Retention: observations are deleted after 24 hours by both the app and the engine. The app can shorten that to 1 or 6 hours; it writes the choice to `meta.retention_hours`, which the engine honours up to 24 and never beyond.
- Exclude list from day one; never read secure text fields. The user's additions are `exclude.json` (`ExcludeList.swift`), edited in the Exclude List window. A site is stored as a pattern that matches its host and subdomains only, not pages that merely mention it. On every change the capture layer reloads its policy and deletes stored observations the new list covers; a list that cannot be read stops capture and is never overwritten.
- Nothing leaves the device except the minimal, redacted snippet on an explicit escalation call.

## Components

| Component | Path | Role |
| --- | --- | --- |
| App | `app/Didja/` | Menu bar UI, observation writer, starts the bundled engine |
| Capture | `app/Capture/` | `CaptureCoordinator` (triggers, debounce), `AXCapture` (tree walk → lines), `AppProfile` (how each chat and email app is labelled), `OCRCapture` (fallback), `Differ` (per-window new lines), `Privacy` (denylist, private windows) |
| Profiles | `profiles/` | One JSON file per chat or email app or site, with fixtures; bundled into the app, read by capture and the engine |
| Engine | `engine/src/` | `extract` (checklists), `match` (completion, from Milestone 2), `store` (SQLite), `engine` (poll loop), `cli` |
| Schema | `schema/` | Applied by whichever side opens the database first |

## Implementation notes (Milestones 1–2)

How the text is shaped:

- `AXCapture` turns the accessibility tree into lines. Inline pieces (bold, inline code, links) are joined into the line of their paragraph or list item, list markers ("1. ", "• ") are kept, and nested lists are indented two spaces per level. That is what lets the engine see "1. Set `FOO` in Vercel" as one numbered line.
- An observation's `text` is only the lines that were not in that window's previous snapshot, so the engine reassembles a window by reading its recent observations in order.
- Inline code is wrapped in backticks, which gives exact boundaries for commands. A list item's further paragraphs and code blocks are indented under it.
- In Claude desktop and claude.ai the engine keeps only lists that follow a "Claude responded:" label. Your own messages, and views with no labels (a document preview), are ignored.
- When the window title is just the app's name (Electron apps), the title of its web page is used instead, so tasks group by conversation.

How completion works (tiers 1 and 2):

- **Markers** are pulled from each task when it is captured: env var names, URLs, commands (backticked, a line of a code block, or recognisable in prose) and file names.
- **Context:** a command counts only when run at a prompt in a terminal app (SCR-61, `commandOutcome` in `match.ts`): the command ends a line right after a prompt character, and within 5 minutes the same window shows output or the next prompt after it (capture reads a terminal's input line too, so a command typed but not entered is on screen alone). The lines between it and the next prompt (a line holding the same prompt text) must not match `FAILURE_LINES` (error:/fatal:, npm ERR!, command not found, `** BUILD FAILED **`, HTTP 4xx/5xx, curl errors, rejected pushes, `[ERROR]`, non-zero exit codes, N failed tests…), and that prompt must not show a non-zero status (✘, ✗, `[1]`). A failed run neither ticks nor asks; a later run that succeeds ticks. The output often comes in a later observation, without the command's line (already kept), so the engine gives `findSightings` the terminal windows' last 5 minutes of observations, joined by window title only. An env var or URL counts only on the site of the service the task names, and only if it names exactly one; "copy X from Supabase into Vercel" is ambiguous and stays manual. File names are recorded but not yet used.
- A task is ticked when every required marker has been seen after the task was created. Claude windows never count, since the task text itself is on screen there.
- Because observations hold only new lines, an env var that was already on the page before you acted does not produce a sighting.
- **Evidence** records each sighting as a description written by the engine ("Ran `supabase db push` in Ghostty", "Saw FOO on vercel.com/…"), never raw screen text, and without query strings.

What counts as a task (asked of you, versus stated by Claude):

- Claude writes lists of things for you to do, and lists that report what it did or plan what it will do. They look alike. Only the first kind become tasks.
- **Per list:** the line introducing the list decides who it is for. A line addressed to you ("you need to", "on your side") makes it yours. A line where Claude speaks of itself ("I'll…", "here's what I did") or a report heading ("What changed", "Plan", "Verified") makes it Claude's, and the whole list is skipped.
- **Per step:** within a list, only steps that read as instructions are kept (an imperative, optionally after "then", "in Vercel,", "if there is no value:"). Statements such as "After that, the rest of Milestone 3" or "The cache was stale" are dropped.
- **The text after the list** counts too. A closing offer to do the work ("Say go and I'll start", "Want me to…?") shows the list was Claude's plan, even under a neutral heading. "Tell me when that's done" does not: there Claude is waiting for you. Because a reply streams in, the list is usually seen before that closing line, so tasks already made from it are taken back (dismissed, with a note) when the line arrives. Tasks you had already ticked are left alone.
- A list not marked as yours must be mostly instructions to be taken at all. A list that keeps a single step becomes a loose task, not a checklist.
- Wording does not always say. "Next steps" or "Order of work" can introduce either kind.

The on-device model (for lists whose wording does not settle it):

- Such a list is taken at once, so it shows up without delay, and queued. When it has stopped changing for six seconds, the engine asks Apple's on-device language model one question: is this list, as a whole, for the user or the assistant's own?
- If the model says it is Claude's own, the list's still-open tasks are dismissed, each with a note that `why` shows. Tasks you already ticked, snoozed or dismissed are left alone. The verdict is remembered by a hash of the list, so the same list is never asked about twice and does not come back.
- The model is asked only about the whole list. Asked step by step it was right about 70% of the time in testing, which is worse than the wording rules, so steps are still filtered by wording.
- How it is called: the engine runs the app's own binary as `Didja --judge` (`Judge.swift`), passing the lead-in, the steps and the first lines of text after the list as JSON. Only `SystemLanguageModel` is used, which runs on this Mac. The framework's Private Cloud Compute model must never be used.
- No model (older macOS, Apple Intelligence off, or the engine run outside the app bundle): the wording-based result stands.
- A local model (maintainer's exception, 2026-11-12): with `meta.local_model` set (`didja local-model on <model>`, or Settings › General), the engine adds `local: { model }` to `--needs-reply` and `--looks-done` requests only (`engine/src/localmodel.ts`). The app's judge then asks Ollama at `http://127.0.0.1:11434/api/chat` first (`LocalModel.swift`: same instructions and prompts, a JSON-schema answer, temperature 0, no thinking, no proxy) and Apple's model when Ollama does not answer cleanly. The reply's `model` says which answered. List judging, titles and chats stay with Apple's model until they have samples to measure on (`engine/eval/ollama.ts`).
- The same model writes a short title for a checklist whose introducing line does not work as one (long, a full sentence, or Claude talking about itself): "I can't change that setting for you, and…" becomes "Remove and Add Accessibility App". It is asked once per checklist, after the list has settled (`Didja --title`), and the result is kept in `model_title` ([`schema/007_model_title.sql`](../schema/007_model_title.sql)). Your own rename always wins, and `why` shows the original line.
- Measured on 20 hand-labelled lists from real sessions: 18 right. Both misses kept a plan that was Claude's; none dismissed a list that was the user's. That is a small sample, and a wrongly dismissed list is recoverable from the Dismissed view.

How the tree is built:

- The capture layer indents nested list items, so the engine sees a step's sub-bullets under it. Sub-items that are themselves things to do become steps under that item, to any depth; statements among them stay with the item as context. A one-word item ("Vercel") is kept only as a heading over real steps.
- A parent carries no markers of its own; its steps do. Completion travels up through every level and ticks travel down (`Store.setStatus`).
- A step first seen on its own that later gains sub-steps becomes their parent, keeping its id.
- You can rename any item. The captured title is kept beside your name (`custom_title`) and is what later sightings are matched against, so a renamed item is not captured twice. Parents remember whether they are folded (`collapsed`). Both are changed through the engine (`rename`, `collapse`, `expand`).

Looks done — confirm? (tier 3, for tasks with nothing exact to match):

- Applies to open steps that cannot tick themselves ("Check the login flow works", "Add the redirect URL in Supabase auth settings").
- A later screen outside Claude is worth a look only if at least two of the task's telling words appear on it. The lines around those words, at most about 900 characters, are shown to the on-device model with the app and page, and it answers done, not done or unsure. "Done" means the screen shows the outcome (a success message, the new thing being there), not a mention, documentation, code, an unused form or an error.
- Which screens: two of the task's keywords on it, and only a screen that is where it gets done: a site or app the task names, or the site of a link its email gave (`isWhereItIsDone`). A task that names no site or app is not checked this way. Chat tasks are never checked this way; your reply in the chat settles them.
- The model's "done" never ticks anything. The task is marked "looks done", with where it was seen, and waits: **Yes, done** ticks it, **Not yet** keeps it open and stops asking from that place.
- Unless you choose **Looks Done: Accept Automatically** in the panel's menu (off by default). The app writes `meta.looks_done = accept`; the engine then takes every waiting suggestion as a yes, ticks the task, keeps the place in `tasks.accepted_from` (schema 012) and notes it in `why`; the row is labelled "auto-accepted". Reopening such a task records the place as rejected, exactly like **Not yet**, so it is never ticked from there again.
- The same lines are never shown to the model twice for the same task (a hash is kept, not the lines), and at most two questions are asked per pass.
- What is stored is where it looked done ("Google Chrome — supabase.com/dashboard/…", no query string), never the screen text.
- Measured on 14 made-up but realistic cases: 12 right, one wrong "done" (a Publish button still waiting to be pressed). A wrong suggestion costs one click on "Not yet".

Teaching the model (SCR-24):

- The on-device model has four jobs: who a list is for (`--judge`), checklist titles (`--title`), emails (`--needs-reply`) and looks done (`--looks-done`). Each has built-in instructions in `Judge.swift`.
- Your own instructions for a job (`brain` table, schema 013) replace the built-in ones for that job; the engine sends them with each question as `teach.instructions`, and `Judge.compose` puts them in place of the built-in text (at most 4,000 characters). Hebrew emails still get their Hebrew guidance after yours.
- Corrections (`lessons` table): **Not an Action** dismisses a task (and its steps) and records each step's wording; a step with that wording is never captured again, and for a task from an email, that conversation (by subject) makes no more tasks. **Not Done** on an auto-accepted task reopens it (so that place never ticks it again) and records the case for "looks done". The last 12 corrections per job are sent as `teach.examples` and appended to the instructions as cases to answer the same way.
- The app's **How It Decides…** window shows the instructions per job (yours or built in) and the corrections, and changes them only through the engine (`didja brain show | set <job> | reset <job> | forget <id>`). Copy puts only the instructions on the clipboard, never the corrections.

App profiles (SCR-42):

- What is particular to one app, which elements are a chat message, its sender and time, an email's header, lives in `profiles/<id>.json`, not in Swift. A profile says which app (`bundleIds`) or site (`urlPrefixes`, or exact `hosts` over https) it is for, and lists rules. Each rule matches elements (`where`: role, `AXIdentifier`, DOM id, class names; all must hold) and is one of a fixed set of actions: `chatName`, `message`, `messageList`, `reactionList`, `skip`, `line`, `emailHeader`, `emailSubject`, `emailSection`, `emailMessage`, `emailBody` (`AppProfile.swift`, documented in `profiles/README.md`). Text comes from a `Source`: an attribute of the element or of the first (or every) element under it that matches, cleaned (`squash`, `dropLabel`, `trim`, `reject`) and optionally cut down by a pattern.
- The walk (`AXCapture.Walk`) is generic over `AXElement`: `LiveElement` reads a running app through Accessibility, `OutlineElement` an outline written down as text. The same code reads both, so a profile is tested against a fixture with no app running (`Didja --profile-test <fixture.json> [--profiles <folder>]`, `ProfileLab`).
- A profile can only label what the walk already reads, in the window already being read. The walk checks secure fields, the exclude list and the draft being typed before any rule runs, and a rule's `Source` checks them again for each element it reads. A profile cannot name another app, run code, or reach the network. Patterns are checked as the profile loads (`ProfilePattern`: at most 300 characters, no back-references or look-behind, no repeated group that repeats inside, input cut at 2,000 characters). A profile that fails its checks is left out and logged.
- The app bundles `profiles/*.json` as `Contents/Resources/profiles` (a build phase copies them). The engine reads the same files (`profiles.ts`) for which windows are chat (by `kind`, the app's name from `name`) and which are mail; `didja profiles` lists them.
- Fixtures (`profiles/fixtures/<profile>-<case>.json`): an outline of the app's window with made-up text, the `lines` capture must keep from it (checked by the app's `ProfileFixtureTests`), and what the engine must make of those lines (`expect`, checked by `engine/test/profiles.test.ts`): the messages with their senders and the asks left open, or the emails. The engine's check stands in a judge that ticks whenever it can (every message from someone else asks, every reply of yours settles), so a message wrongly read as yours shows up as an ask missing from `open`.

Diagnostics and your own Claude (SCR-42):

- **Report a Problem with This Window…** (`Diagnostics.swift`): `CaptureCoordinator.readForDiagnostics` reads the last app in front (not Didja) once, on the capture queue, after the same exclude-list, title and address checks as capture: an outline copy (`OutlineElement.copy`: secure fields as their role only, the focused draft without its value), the lines capture keeps, and the last 80 kept lines of that app (`ObservationStore.recentLines`). The app adds its tasks and `didja why` for each. `DiagnosticsReport` holds each line raw and masked (`Redactor`); the preview shows the masked file and shows a line as it is only when you click it. Nothing is written except by Save…, Copy, or Give to My Claude.
- **Propose Upstream…** (`Proposal.swift`, How It Decides): `InstructionProposal` is your saved instructions for a job, a line diff against the built-in ones, a note, and only the corrections you tick, as JSON (`kind: didja-instructions-proposal`). `engine/eval/compare.ts` runs a proposal and the built-in instructions on the job's made-up samples through the built app's model (`teach.instructions` replaces the built-in text, as for your own): emails (`mail-samples.json`) and looks done (`looks-samples.json`, where answering done on a screen that does not show it is a wrong tick). It says take only when the proposal gets more right with no new wrong ticks.
- **`didja mcp`** (`engine/src/mcp.ts`): an MCP server over stdio, built on the SDK the engine already uses for Connections, with plain JSON-schema tools (`list_reports`, `read_report`, `observations`, `why`, `list_profiles`, `show_profile`, `draft_profile`, `test_profile`, `draft_issue`). The server's `instructions` (`INSTRUCTIONS`) tell the client to offer `draft_issue` after a diagnosis and to show the draft first. `draft_issue` (`issue.ts`, SCR-57) fills a fixed template matching `.github/ISSUE_TEMPLATE/missed-task.yml` and `app-support.yml` (the form's field ids are the link's query parameters; a test keeps them equal): the fingerprint `<bundle id>:<miss>`, app and profile, versions (`CFBundleShortVersionString` beside the app binary, `sw_vers`), Claude's three fields, and what capture kept, masked by `mask` after email addresses are masked whole. Before and after drafting, `leaks` refuses an unmasked email address, a link with a path (other than the repository's), a number of three or more digits with any digit but 0, and any word of the case's raw text (the task, its why, kept lines and window titles, or the report) that is not a label word, a common word or the app's name (`contentWords`). A report is masked again, lines the user chose to show included. Links over 7,000 characters give the bare form and the body to paste. Every call is checked against `meta.mcp_enabled` (`didja mcp on|off`, the switch in Settings › General) and appended to `mcp-log.jsonl` with its arguments shortened, never its answer. Kept text and `why` are masked by `mask`, whose word list a test keeps equal to the app's. Files are read only from `Shared with Claude/` and written only to `Profile drafts/`, by plain file name. `test_profile` runs the app's `--profile-test` (with the drafts folder) and the engine's `engineView` (`fixtures.ts`, shared with the tests).

Canvases (SCR-49): `canvases` and `canvas_items` (schema 019). An item is a task (by id: the task itself), a note or a heading, ordered by a real-valued position (moving takes the midpoint). `Store.sendToCanvas` puts a checklist in as its title (a heading) and its steps. The app's `CanvasWindows` shows each canvas as a floating `NSPanel`, reloaded every 4 seconds while open; `CanvasDirectory` keeps the list for menus in memory, refreshed after each change, so drawing a row never runs the engine.

Email (Outlook for Mac; Gmail and Outlook on the web in a browser):

- The capture layer labels each open email as its own section, named after its subject (`⟦Email: Q3 budget numbers⟧`), with `From:`, `Date:` and `To:` lines followed by the body (the app's profile: `profiles/outlook.json`, `gmail.json`, `outlook-web.json`). In Outlook that is the reading pane; its sender and recipients sit in elements that are not plain text, so without this they are not captured at all. In Gmail (a page at `mail.google.com`, recognised by its class names) every message of an open thread is a section, `⟦Email 2: …⟧`, and what follows a message goes under `⟦Page⟧` so it is not taken for body text. Outlook on the web (`outlook.cloud.microsoft`, `outlook.office.com`, `outlook.office365.com`, `outlook.live.com`) is recognised by the DOM ids its reading pane gives each part of a message (`MSG_…_SUBJECT`, `_FROM`, `_TO`, `_DATETIME`, `UniqueMessageBody…`); like Gmail it shows names, not addresses. The message list is not read.
- The engine (`email.ts`) considers an email only if it arrived today or yesterday, has a body, is not automatic (calendar replies, auto-replies, newsletters and marketing with an unsubscribe line are always skipped; mail from a service address such as `no-reply@` or `billing@`, and receipt-like subjects, are skipped unless they say something needs doing on your side, such as "update your card", "action required", "expires" or "payment failed") and is not your own message. The rest go to the on-device model with the sender's name, the subject and the first 900 characters. The model answers three things in order: does the email explicitly ask for anything, what is the thing to do (3 to 9 words), and is it done by writing back or somewhere else.
- The task is titled with the thing to do, "Send Dana the updated Q3 numbers" or "Update card details on PayPal", not "Reply to…". If the model's wording is unusable the title falls back to "Reply to Dana Levi: Q3 budget numbers". The sender and subject are kept as a note on the task (`why` shows it).
- An email is known by a hash of its sender, subject and time (`mailKey`), and the task it became is recorded against that (`email_tasks`). Reading it again, because more of it loaded or the question put to the model changed, rewords that one task; it never makes a second, and never brings back one you finished or dismissed. A task made before emails were linked is found by its old "Reply to <sender>: <subject>" title or the subject in its note, and counts the same way whether it is open, finished or dismissed.
- A forwarded email (an "Fwd:" subject or a forwarded-message marker) is shown to the model as forwarded, with the sender of the quoted header, and the model is asked who wrote the request: the name it is signed with. That person, not the forwarder, is noted on the task, and a title that names the forwarder is corrected to name them.
- An email written mostly in Hebrew (more Hebrew letters than Latin ones, `Judge.isHebrew`) gets one extra paragraph of instructions: write the task in Hebrew, name the person or company from this email and never one from the examples, and copy a signature with a role in it whole (נועה - מש"א). English mail gets the instructions it always had; Hebrew examples in the shared instructions leaked into English tasks (SCR-11).
- The model tends to cut a signature short at a quotation mark, or to join the full name from the header to the role. `signedName` completes it from a short line of the message: one that starts with what the model gave, or one with the same first name and a role that starts the same way.
- Prompt work is measured with made-up emails: `cd engine && bun eval/mail.ts` runs `engine/eval/mail-samples.json` through the built app's model and prints each result. It is not part of `bun test`: it needs Apple Intelligence.
- A sender that is only an address, or a service address (`service@`, `no-reply@`…), is never waited on for a reply: what it asks is treated as something to do elsewhere.
- Your own messages. Gmail says "to me", so a message not addressed to you is skipped. Outlook shows names instead, so the engine learns who you are from the window title: Outlook for Mac's main window is titled `<folder> • you@example.com`, Outlook on the web `Mail - Your Name - Outlook` (`accountOf`). Only those exact shapes count, so an address in a message window's subject is never taken for yours. Once an address is known, the name a message sent from it carries is learned too, so it still counts where only the name is shown. Up to six addresses and six names are kept in `meta.mail_identity`. A message from you (`isMine`: by address where one is shown, by name otherwise) makes no task; it is still recognised as your reply in a conversation you were asked to answer (SCR-10).
- Workflow responses (SCR-55). An approval workflow's Approve, Reject or Forward link opens a new email to the workflow, not a reply: the request's subject without "RE:", another recipient, and a body line such as `Response Action: 'Approve'` (`responseAction`, which takes only that whole line with the choice in quotes). An email with that line, sent as you (`isMine`), ticks the open or snoozed email tasks of the same mailbox whose request had exactly that subject (`mailTasksWithSubject`, from the origin note; `tickByResponse`). Any choice settles it: rejecting or forwarding it is also an answer. Reopening it marks that place rejected, so the same response never ticks it again. Not linked: a response with another subject, from anyone else, in another mail app, or without the line. In one window, a second email with the same subject is read as the first one again (`parseEmails`), so a response is only seen in a window of its own, such as Sent Items.
- Outlook's reactions summary beside Reply (a button described "1 Like … reactions") becomes `Reactions: 1 Like` in the email's section (a `line` rule in `profiles/outlook.json`), kept as `Email.reactions`, not body. On the email of a task still awaiting your reply it suggests done, never ticks: it does not say whose reaction it is.
- Outlook reads the sender's presence out after the name ("Dana Levi Available"); it is dropped.
- Where an answer is wanted, a reply is noticed without the model: a message in the same conversation (same subject once "Re:" is removed) from someone other than the person who asked. That only asks you to confirm; nothing is ticked. Where the thing is done elsewhere (a website, a form), the task is watched like any other with nothing exact to match, under "looks done — confirm?".
- Following the email's link (`followLinks`). The links in an email's body are kept on its task as the pages they point to, with mail-filter wrapping removed (Proofpoint, Safe Links), and only if they name one page: a path or a record id, never a site's front page. When you are later on that very page (same site, same path, every record id of the link in the address), the on-device model is shown what is on it. The task is ticked only if the model says done **and** you had already been on the page for at least 10 seconds, so that what it judged appeared after you arrived rather than being the page as it loaded. A "done" on arrival only asks you to confirm. A task ticked this way and reopened by you is only ever asked about afterwards. This is the one place the model's judgement can tick; the exact part is the link, which comes from the email itself. For a link whose words are not its address ("Approve", "click here"), the capture layer writes the target after the words, `Approve ⟨https://…⟩`. It does this only inside an open email's body (Gmail, Outlook on the web, and the message web area in Outlook for Mac), and only for web addresses of at most 500 characters; links on every other page are read as their words only.
- E-signature requests (`esign.ts`): an email task with a DocuSign/Adobe Sign/Dropbox Sign/PandaDoc/SignNow link is ticked when, after a page whose address carries the request's own long id (path or query, never `er`/`acct`-style ids naming a person or account), that service shows its finished message ("A copy of this document has been saved/sent", "You're done signing"…) within 15 minutes. No model involved.
- Archiving (`ArchiveWatcher.swift`). A mail app shows a notice after archiving ("Archived" in Outlook, "Conversation archived" in Gmail). As recorded in Outlook for Mac, the email leaves the reading pane first and the notice shows up to a second later. So when the notice appears, the email that most recently left the pane, if it left within 4 seconds, was archived; the capture layer then writes `⟦Archived email: <subject>⟧` into that window's observation, and the engine dismisses that mailbox's open tasks for the subject (dismissed, not ticked: archiving does not say the thing was done). An email leaving with no notice is just you clicking another; a notice with nothing having left is something else being archived; archiving again while the notice is up is caught only when Outlook replaces the notice (it goes away for under a second and comes back) and a capture lands in that gap. After an email leaves or the notice goes away, the window in front is captured seven more times over the next 2.8 seconds to catch it. An email that leaves while the notice is up is not taken as archived on its own: in the recorded session one did and came back five seconds later. Archiving from the message list, with no email open, is not detected: nothing on screen says which email it was without reading the list. Outlook on the web has not been recorded yet.
- Text on a mail screen never ticks or suggests any other task.
- Each email is put to the model once (a hash of sender, subject and date is kept, [`schema/009_email.sql`](../schema/009_email.sql)).
- Measured on 14 made-up emails: 12 right; the two misses were a receipt and a calendar invitation, which the automatic-mail filter now removes before the model is asked.

Chats (WhatsApp, Teams; Slack built but not tried live):

- The capture layer labels each message of the open conversation as its own section, carrying the chat so it stands on its own (capture passes on only new lines, each under its own section line): `⟦Chat message: Dana Levi (direct) — from Dana Levi — Today at 9:05⟧`, then the message's lines (`ChatAdapter.swift`, from the app's profile in `profiles/`). Kind is `direct`, `group` or `unknown`; the sender is the name shown, or `me` where the app says so.
- WhatsApp for Mac: the open chat is `ChatMessagesTableView` ("Messages in chat with …"); each message is a `WAMessageBubbleTableViewCell` whose description holds kind, text, time and "Received from …" or "Sent to …" (parsed from the end, so commas in the text survive). In a group the label starts with the sender and says where it arrived: "Message from Ron, …, 10:54, Received in Family"; that marks a group, as does someone other than the chat's own name writing in it. Today's messages carry the time alone ("10:54").
- Teams: `chat-header-<thread id>` names the chat (the people it lists as `chat-topic-person-…` in a one-to-one chat, whose heading is only "Chat participants"; otherwise its heading); ids ending `@thread.v2`/`@thread.tacv2` are groups. Each message is `message-body-N` with `author-N`, `timestamp-N` and `content-N`; a message titled "… mentioned you" is flagged; system notices (`fui-ChatControlMessage`) are left out. A message that follows on from the one before takes its author and time.
- Slack (from its class names: `c-message_kit__background`, `c-message__sender_button`, `c-timestamp`, `c-message_kit__blocks`, `p-view_header__channel_title`): kind is always `unknown`, treated like a group.
- The engine (`chat.ts`, `readChat` in `engine.ts`): a message from someone else, recent (time shown within three days, `chatTime`), with words in it, and in a group (or unknown) naming you (`namesMe`: an @mention flag, or one of your names or first names as a word), is put to the on-device model once (`Didja --chat`): does it ask you to do something, and what. Your names (`myNames`) are the name you set in Your Names… (`meta.my_chosen_name`) or else your Mac account's full name, which the app writes to `meta.my_name`, then the other names and nicknames you add (`meta.my_other_names`), then the ones your mail is sent under; they are shown to the model only for group chats (shown for a one-to-one chat, it named you instead of the sender). An ask already followed on screen by a reply of yours that does not put it off is skipped. The task is filed under `WhatsApp — <chat>`; its criteria keep the app, chat, sender, when it was sent and the message's key (first line, so a message whose text arrives in pieces stays one).
- A live conversation is not a task per message (SCR-45). An ask sent less than 10 minutes ago (`CHAT_ASK_WAIT_MS`) is put to the model as before, then parked in `chat_pending` (schema 018: the model's wording, sender, chat and time, never the message). A reply of yours in that chat that does not put things off, seen with a readable time, drops the asks sent before it (`answerPendingChatAsks`). Every poll, asks that waited 10 minutes become tasks (`promotePendingChatAsks`), whether or not the chat is on screen; an ask with an unreadable time is not parked. A chat has one open task (`openChatTask`): a new ask joins it (`addAskToChatTask`), which rewords it to the newest ask with "· +N", points its criteria at the newest ask (so your next reply settles the conversation) and clears a "looks done" it showed. Once, open chat tasks already made per message were merged into each chat's newest (`foldChatConversationsOnce`, `meta.chat_conversations_folded`). The chat instructions say a statement about the sender (plans, wishes, offers) or a question already answered is not an ask, and word a question "Answer <name>: <question>"; `chatTaskTitle` refuses vague wording ("what he thinks").
- Reactions: WhatsApp's chat list rows (`ChatListView_TableView`) reading "You reacted 👍 to "…"" become `⟦Chat message: <chat> (unknown) — from me — reaction⟧` `[reacted 👍 to “<first line>”]` (the badge under the bubble is not exposed; the rest of the list is not kept); the engine takes such a reaction as answering the ask whose first line it names (`lineHash`, `reactedTo`), whenever made. Also WhatsApp's "You reacted ❤️ to "…"" and Teams' checked reaction pill (`diverse-reaction-pill-checked`, titled "1 Heart reaction.") become a message from you right after the one reacted to, `[reacted ❤️ to “…”]`. A reaction or an emoji-only reply that the model calls settling only asks you (`isReaction`, `isEmojiOnly`). Chat tasks are not watched by "looks done" (`tasksToWatch`).
- Ticking: a message of yours in the same chat, sent after the ask by the time shown (in the same minute, also below it; an unreadable time never counts, since lines arrive in the order they were seen, not sent), is judged: a reply that plainly puts it off (`plainlyDefers`: later, tomorrow, I'll check, אחזור, מחר…) never ticks; otherwise the model (`Didja --chat-reply`) says `settles` (ticked, labelled, `Store.tickByReply`), `defers` (stays open) or `unsure`; unsure, or no model, only asks you (looks done?). Reopening a task ticked this way stops replies in that chat ticking it again.

Only new messages (SCR-27, reworked 2026-11-12; **Older Messages: Ignore Them** in the panel's menu, `meta.only_new = on`, off by default): what is plainly dated before capture started is left out, nothing else.

- When capture started: the app writes `meta.capturing_since` each time its status becomes Capturing (at launch, and on Resume after Pause); `Store.captureStartedAt` reads it. With no such note, nothing is left out.
- Chats: a message is not put to the model if its time is before that minute (`sentBefore`). A time that cannot be read is kept.
- Email: a message is not read if its date is before that minute (`mailTime`: "(2 hours ago)", "Today at 9:15", "Yesterday", a clock time alone, a slashed date read only where one reading falls in the last few days, or a full date). A date that cannot be told is kept; mail older than a few days is skipped anyway (`isRecent`).
- Claude: replies carry no date, so none is left out, also when you scroll back to one, or come back to one that arrived while you were in another window. (The first version left out what was already there when you first looked at a conversation, which also dropped those.)
- Ticking and tasks you already have are not changed by it.

Connections (the one network use; `connections.ts`, `sync.ts`, `ConnectionsView.swift`):

- A connection is kept in `meta.connections` (kind, what to change when an item is ticked, whether to write back when Didja ticks on its own). Its OAuth keys (client registration, tokens, PKCE verifier) are in the login keychain under "Didja connection", through `security`. Sign-in: `didja connect linear` serves `http://localhost:33418/callback` (on 127.0.0.1 and ::1 only; a one-time `state` must come back with the code), opens the MCP server's authorization page in the browser, and finishes with the code it gets back (MCP TypeScript SDK, `StreamableHTTPClientTransport`, `OAuthClientProvider`).
- Sync (`syncConnections`, every five minutes in `run`, and soon after an item is ticked here): `list_issues` with `assignee: "me"` (with each issue's team); the items the connection's `bring` rules ask for (`isWanted`: due today or earlier, in progress, to do and/or backlog; all teams or the ones chosen; never completed or cancelled) become tasks (`sourceKind 'external'`, `criteria.external` with the connection, id, key and address; linked through `email_tasks` as `ext:<connection>:<id>`). Completed there: done here; cancelled or gone: dismissed. Ticked here and not yet written: `save_issue` with the chosen `state` and/or `addLabels`, once (`ext-written:<task>`); ticked on its own (a marker, a reply, accepted automatically) only if the connection allows it.
- Per tool, `adapters.ts`: Linear (`list_issues`, `save_issue`, teams and statuses), Jira (`getAccessibleAtlassianResources` for the site, `searchJiraIssuesUsingJql`, `getTransitionsForJiraIssue` + `transitionJiraIssue`, `editJiraIssue` for labels), Asana (`asana_list_workspaces`, `asana_search_tasks`, `asana_update_task completed`), Todoist (`find-tasks`, `find-completed-tasks`, `find-projects`, `complete-tasks`), Notion (`notion-search` for databases, then their pages; `notion-update-page` for Status). Tools are found by name in the server's own list (`findTool`), arguments cut to those declared (`fitArgs`), answers read wherever their list of objects sits (`objectsIn`); a missing tool is reported (`MissingTool`), never guessed. Each kind lists its servers, newer transport first, then SSE; the one that answered is kept on the connection.
- The app reads the key and address from `criteria` for the row's label and talks to the engine for everything else.

The same thing in two places (`related.ts`, schema 015): tasks from chats, emails and connected tools, created within three days of each other in different places, from the same person (chat sender; email origin note's name without "via …") and about the same kind of action (`actions`), are put in `merge_suggestions`. The app shows the question on the open one. `Store.merge` sets `merged_into`; `Store.setStatus` gives merged tasks the same status; the app leaves merged tasks out of the list and labels the one kept.

How a window's text is put back together: an observation holds only new lines, each batch under the section line of the message it belongs to, so a streaming reply or an email whose body loads late arrives in pieces. Before reading, the engine gathers every section's lines under one heading (`assemble`).

Commands Claude tells you to run (`extractCommands`): in a message that is not yours, a line holding only a shell command in backticks (`commandLine`: a known program first) becomes a step when the line before hands it over (ends in ":" or "run/paste/type/enter") or a line after mentions the Terminal or pasting; "I ran:"-style lead-ins are Claude's own. They join the window's lists (minus commands a list already holds), so they are judged, grouped and ticked like list steps; the command is the marker.

How checklists are grouped:

- Each checklist becomes a parent task (`is_group`) named after the line that introduced it ("Before this works in prod"), or failing that the opening words of Claude's message. Its steps point at it with `parent_id`.
- Steps already known keep their parent, so a list seen again, or still streaming, lands in the same group.
- The engine keeps parent and steps consistent in one place (`Store.setStatus`): a parent is done once no step is open, reopens when a step does, and ticking, dismissing or reopening a parent does the same to its steps. The menu ticks by calling the bundled engine, so the rules live only there.
- A task can be added by hand (SCR-29: `addManualTask` in `engine.ts`, CLI `add <title>`; in the app the A or + key, or the + button, in the panel and the task window). Its source is `manual` / "Added by you". It gets markers and criteria from its title like a captured step, so it is ticked by the same rules (a command at a prompt, an env var or URL on the named service, "looks done" where it gets done), only from observations after it was added. It is never merged by wording with another task (`distinct`).
- A whole conversation can be ticked at once (`Store.completeSource`, CLI `done-all <id>`, where the id is any task from that conversation). It ticks the conversation's open checklists and open loose tasks through `setStatus`, so the same rules apply. Top-level tasks that are snoozed or dismissed are not touched. In the app this is the circle on a conversation's heading and the C key, which acts only when the highlighted row is listed as pending, and never while a search hides rows (`TaskNavigator.isNarrowed`).

Additions to the schema above, all additive:

- `tasks` also has `dedupe_key`, `position`, `created_at`, `last_seen_at`. The same list is seen many times, and streamed or truncated lines differ slightly, so tasks are deduplicated by normalised title with a near-match check. The normalised title (`dedupeKey`) keeps the letters and digits of every script, lowercased, with accents and points dropped (SCR-62); a title with none of them is keyed by its exact wording and never near-matches anything, and no lesson ("not an action", "not done") is stored or looked up under an empty key.
- A `meta(key, value)` table holds the engine's cursor.
- `tasks.confidence` currently means "how sure are we this is a real to-do" (share of items in the list that read as actions).
- `tasks` also has `parent_id`, `is_group` and `done_at` ([`schema/003_groups.sql`](../schema/003_groups.sql)).
- `tasks` also has `custom_title`, `collapsed` and `auto` ([`schema/006_tree.sql`](../schema/006_tree.sql)).
- `tasks` also has `suggestion` and `suggested_at`, and `looks_done_checks` remembers what the model was already asked ([`schema/008_looks_done.sql`](../schema/008_looks_done.sql)).
- `judgements` and `pending_judgements` ([`schema/005_judgements.sql`](../schema/005_judgements.sql)) hold the model's verdicts and the short-lived queue.
- `evidence` also has `kind`, `marker` and `detail` ([`schema/002_evidence.sql`](../schema/002_evidence.sql)), so it stays meaningful after its observation expires and `observation_id` becomes NULL.

The app's UI:

- Names (SCR-37): the app calls the panel the **Quick View** and the task window the **Full View**, from `ViewNames` (one place for both names). The code keeps panel/popover and task window.
- The menu bar icon and its panel are an `NSStatusItem` and `NSPopover` owned by the app (`MenuBarPanel`), not SwiftUI's `MenuBarExtra`, which cannot be opened from code and so cannot serve the hot key. The panel's content is SwiftUI (`TaskViews.swift`). It reads tasks straight from SQLite every two seconds, and makes every change by running the bundled engine (`done`, `done-all`, `reopen`, `snooze`, `dismiss`, `why`), so the rules live in one place.
- Pinned panel (SCR-25): `MenuBarPanel` also owns an `NSPanel` (utility style, floating level, resizable in height only, 440 wide) holding a second copy of `PopoverView` with `pinned: true`, whose list fills the window rather than sizing it. While a frame is saved under `pinnedPanelFrame` in the app's user defaults, `show()` opens that window at the frame instead of the popover; moving or resizing it saves the new frame. `PanelPlacement.fitted` puts a saved frame back on the screens there are now (the display it overlaps most, or the first screen's top right if that display is gone). Unpinning deletes the key.
- Closing when you go elsewhere (SCR-30, SCR-39): the panel, under the icon or pinned, closes on any of three signals: Didja resigning active, `NSWorkspace.didActivateApplicationNotification` for another app (which also covers the case where opening the panel never made Didja the active app), and a global mouse-down monitor installed while it is shown. `MenuBarPanel.closesOnOutsideActivity` decides, ignoring the first 0.4 s after opening (pinning closes the popover and reopens the panel as a window, and the app you came from can come to the front in between). The `panelStaysOpen` user default ("Keep Quick View Open When You Click Elsewhere", `PanelStaysOpen`, off by default) turns all three off and switches the popover from `.transient` to `.applicationDefined`.
- The task window offers the same list by state. Its header has a way out (SCR-36, `WindowExitButtons`): **Quick View** or O runs `WindowExit.backToPanel`, which closes the window, then shows the panel, and reopens the window if the panel cannot be shown (a hidden icon and no pinned spot); × or Esc closes it. `TaskBoard` is the pure model both use. Each top-level row shows how long ago it was captured, from `tasks.created_at`; the wording is `CapturedLabel`, a pure function of the capture time and the clock, redrawn each minute.
- Keyboard: `GlobalHotKey` (`HotKey.swift`) registers ⇧⌘J (until 2026-11-12, ⌃⌥S) with the Carbon hot key API, which needs no permission and reports only that combination. The panel's keys can be changed (SCR-40): `HotKeyShortcut` is the key code and Carbon modifiers, saved as `panelHotKeyCode` and `panelHotKeyModifiers` in user defaults (absent means ⌃⌥S) and checked by `problem` (a named key; ⌃, ⌥ or ⌘ unless it is an F-key; not ⌃⌥P; not a few combinations macOS keeps). `PanelHotKey` owns the registration and swaps it, keeping the old keys when the new ones are refused or owned by another app. Settings › General › Keys records the keys with `HotKeyRecording`, a local key-down monitor that suspends the old hot key while you choose. The pause key (⌃⌥P) is not changeable. MenuBarExtra cannot be opened from code, so the hot key presses the menu bar button (`MenuBarPopover`); if the button cannot be found it opens the task window instead. Key presses in the popover and task window are caught by one local event monitor in `AppDelegate` and handed to a `TaskNavigator` (one per list), which holds the highlighted row and is pure enough to test. Keys are matched by key code, so they work in any input language. An action key does nothing unless a row is highlighted and still in the list. Several rows can be chosen together (`TaskNavigator.marked`: ⌘A, ⇧↑↓, ⌘-click, ⇧-click), only from the rows on show, so under a search ⌘A chooses the matches only; the choice is dropped when the view, conversation or search changes, and rows that have left the list are skipped. Space, S and D then go to every chosen row: a step whose checklist is chosen too is left to the checklist (`TaskNavigator.outermost`), S and D touch open rows only, and Space ticks the open ones, reopening only when none of them is open. Each is one engine command per row, run one after another on a serial queue.
- Copy: ⌘C, a row's copy button and its menu put the row on the clipboard as plain text. `TaskBoard.copyText` builds it from titles only (a parent with its steps as an indented checklist; no notes, no evidence, dismissed steps left out), and the app writes it to the general pasteboard only on that explicit action. Copying changes no task, so it does not go through the engine. ⌘C is left to whatever is in focus when that can copy for itself (selected "why" text), and passes through when no row is highlighted.
- Snoozed tasks carry `snoozed_until` ([`schema/004_snooze.sql`](../schema/004_snooze.sql)); the engine reopens them when the time comes, and still ticks them if it sees them done meanwhile.

What happens when something is ticked: a finished top-level item stays where it was for three seconds, ticked and struck through, with its steps on show even if it was folded, and only then moves to "Recently done" (`TaskBoard.lingering`). That holds whether you ticked it or the engine did. "Recently done" is folded unless you open it, so a list with nothing left to do shows nothing but its heading.

Onboarding is one screen (`WelcomeView.swift`): what is read, what never is, and both permissions with live state. It opens by itself the first time and whenever Accessibility access is missing at launch.

Reminders: a top-level item left open for four hours with nothing ticked, not snoozed, is reported once by the engine (`didja nudges`, `nudged_at` in [`schema/010_nudges.sql`](../schema/010_nudges.sql)); the app checks every five minutes and posts a notification (`Nudger.swift`). macOS asks for notification permission the first time there is something to say.
