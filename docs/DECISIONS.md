# Decisions

Choices made while building ScrolledAway, with the reason, so they are not re-argued or quietly undone. Newest first. Add one whenever a choice is made in conversation, in Linear, or in code review that the code alone would not explain.

## 2026-11-13

- **The first-run nudge waits for ten minutes and five readings, and ends for good** (SCR-89): one glance at a chat is not a try, and a note that keeps coming back after the first steps, or after you closed it, is noise. It counts readings of AI tool windows only (other apps never make it show), and it ends with the first task from any AI tool, even one you dismissed.
- **The status the app shows is the engine's** (`meta.first_run`), like every rule about tasks: the app only draws it and writes that you closed the note.
- **An unknown AI tool candidate keeps a site's host name** (SCR-89), only when a part of it is "chat" or "ai": it is what you would tell us, and the report already names apps. Never the window's text or title. The troubleshooting report is still yours to send or not.
- **"Try it" suggests a numbered checklist** because a numbered list is what every AI tool writes when asked for one and what Didja reads best; the Copy button puts it on the clipboard, Didja does not type it anywhere.

- **Agent hooks for Claude Code, Cursor and Windsurf only** (SCR-88). Copilot in VS Code's hooks are `.github/hooks/*.json` in a repository, and the issue says never a repository's file. Left out until it has a user-level place.
- **Our entries are known by their command** (` hook <tool> ` and `didja` in it): hooks files are JSON, which has no comments to mark a block with, as the issue asked. A file that is not JSON is never touched.
- **A hook only takes steps back, from its own tool's source.** The same command asked of you in the Claude app stays yours even if Claude Code ran it: the hook says the agent ran it, not that your step was done or not yours. Nothing from a hook ticks a task.
- **Edits are not recorded**: a file path is not among the fields the issue allows (tool, event, time, a command line and exit code, plan titles), so "the agent edited the file a step names" stays SCR-65's screen rule for Claude Code.
- **`didja hook` never opens the database and never fails**: it runs on every tool call of the agent, so it only appends a line and exits 0, whatever it is given; the engine checks which tools are on when it reads.
- **Off forgets what that tool said**: its events are removed from the log, not left for 24 hours.

- **The shell hook is a new local file, opt-in** (SCR-87, as the issue decides): `shell.log` beside Didja's database, kept 24 hours like observations, listed in Privacy, removed with the hook. It holds commands as typed (a key- or token-looking one as a hash only), exit codes and a hash of the folder, never output. Nothing of it leaves the Mac.
- **The engine installs and removes the hook** (`didja shell-hook on|off`), not Swift: it is testable with a made-up home folder, and the app's switch only runs it. ~/.zshrc is created if missing (zsh is macOS's shell); ~/.bashrc and fish only if you already use them. The fish function is a file of its own in conf.d, so config.fish is never edited.
- **Settings › General › Commands, not a new Settings page**: one switch did not need a page of its own.
- **With the hook on, its failure beats the screen**: when every exact run since the step failed, a screen that looked fine does not tick it (a missed tick is cheap). A success in the log ticks like a run seen on screen.
- **A command typed twice in a row in bash is written once**: bash's lines read the last history line and skip it when it has not changed (so an empty Return writes nothing). zsh and fish write every run.
- **p10k's right-side "✘ 1" counts as the previous command's status** only when the line holds nothing else (a status mark or a time is required, so a command such as `at` is not taken for one).
- **Text outcomes needed no new rule for Codex**: its "✓"/"✗" lines are the agent's own runs (SCR-85), and agent windows never tick.

- **While the menu bar is hidden, the Quick View opens as the pinned panel's window, not a popover** (LOCAL-1): a popover needs an anchor on screen, and the icon is not. The window is placed fresh each time (not saved as pinned), so with the menu bar back the icon opens the popover as before. The same happens when the icon is off every screen with the menu bar showing (hidden behind the notch, say), where the hot key used to do nothing.
- **Outside activity is ignored for 0.5 s after opening** (was 0.4 s), as the issue asks, so the menu bar sliding in or out as the panel opens does not close it.

- **A listed target is evidence, not a tick** (SCR-86, as the issue says): it joins the model's "done" as the second sign, asks when there is no model, and ticks alone only at an earned-trust place. Being listed is strong but not proof the step was done after it was asked (a row may have existed already).
- **Env and URL markers on a catalogued site now need the item in the right list.** Before, the name anywhere on vercel.com ticked (a build log saying it is missing would have). Sites the catalogue does not know keep the old rule. Measured: no benchmark tick was lost.
- **The place must be named by the step or its source** (the maintainer's rule from SCR-66), with other names per service ("Google Console"). A GitHub settings page is not where "Set the repo to Public" is done unless the conversation says GitHub.
- **Confirming words are whole lines** ("^Valid Configuration$", "^Enabled$"), so "Invalid Configuration" or "Disabled" never pass.
- **A Google OAuth client counts only once saved**: its redirect URIs are an edit form, so the "OAuth client saved" notice is required. A later visit without the notice is a miss, not a tick.
- **The redeploy follow-up is a task beside the step, not under it**, added once per conversation and only when the conversation has no redeploy step; adding a sub-step under a captured checklist would change the list Didja shows as the assistant's. It is added only after an env tick on Vercel or Netlify.
- **No follow-up from a key on screen** ("Add it to <env>" after `whsec_…` appears): that would mean reading a secret off the screen to act on it. Left out.
- **Didja-added follow-ups are listed apart in the benchmark**, since nothing on screen asked for them; counting them as made would lower precision for a step the issue asks for.

- **An agent "doing it" needs the agent to have run it, not just to have asked** (SCR-85). A prompt still waiting, or the cursor resting on "❯ 1. Yes" (where it starts), settles nothing; only a later "ran" line, or a declining answer, does. The cost: an approved run whose "ran" line was not captured leaves the step on your list (a miss).
- **A step is the agent's only when the agent ran its command after the step was listed** (or after you declined it). A run earlier in the session is not this step, as for Claude Code (SCR-65).
- **A taken-back step is dismissed with why, never ticked**, so it shows in Dismissed with "<agent> ran this itself" and Didja's tick counts stay yours.
- **A declined command is kept as yours even if the agent runs it later**, then taken back on that run, so the order on screen decides and nothing is lost if the run is missed.
- **Agent todo items are matched by their words** (letters and digits, any case), in the same window only: a step for you worded like the agent's own item is the agent's; the same words in another tool are not touched.
- **Approval prompts and ran lines are blanked before lists are read** in terminal and editor agents only, never in chats; their line numbers are kept so step order still works.
- **The benchmark counts what is left on the list** (SCR-85). The issue's acceptance is "agent-run steps leave the list"; a step made and then taken back two minutes later (SCR-65's case) was counted as made and as "must not exist", which no change could fix. Taken-back tasks are listed apart, and a tick before a take-back still counts as a wrong tick. The "before" numbers in ARCHITECTURE are re-measured under this rule.

- **Other step shapes are rewritten into the ones the extractor reads, not read by a second extractor** (SCR-84): headings, human-steps bullets, drawn boxes, tables and code blocks become numbered lines, "[ ]" boxes and backticked commands. Who a list is for, the action-share rule, sub-steps and markers then stay in one place, and Claude's existing lists read exactly as before (a test checks text with none of these shapes is unchanged).
- **Bullets count only under a heading or lead-in that hands them to you** ("Next steps", "You'll need to", "On your side", "To finish setup", "Steps"…); bullets elsewhere (notes, "If you want, I can:") stay prose.
- **Drawn boxes ("☐") count only in chat windows.** In a terminal they are an agent's own todo list (Claude Code's, read by SCR-85).
- **Target words are precise**: "API key", "signing secret", "redirect URL", "DKIM", "OAuth client"… but not "token" or "secret" alone, so a note like "The token line is no longer needed" stays a note (an existing test).
- **One step is a list when its lead-in is addressed to you.** SCR-64 found every one-step hand-off missed; a lead-in such as "The only thing left for you:" is as clear as a list gets. A single step with an unclear or Claude-speaking lead-in is still not one.
- **Targets are not stored apart on the task**: the env names, URLs and commands a step names are already its markers (`extractMarkers`, from its title and context), which is what done detection reads.
- **Bold lead-ins with no number are not read**: capture's text has no bold, so a bold line is indistinguishable from a sentence. Bold lead-ins inside numbered lists are read already.
- **Scenario 40's label was too narrow**: it named the env var, which ChatGPT put in the step's paragraph, not its heading "Set the secret in Vercel". The label now names "secret" and "Vercel"; the step is the same.

- **Assistant profiles are read by the engine only** (SCR-83). Capture needs nothing from them: it already sets AXManualAccessibility on every app it reads (`AXCapture.prepare`), Electron editors and ChatGPT included, so the issue's capture step was already true.
- **Claude's profiles keep their source kinds** (`claude-desktop`, `claude-web`, `claude-code`) and are tried first (`order: 0`), so tasks made before group with new ones and Claude is recognised as before. Other tools' source kind is their id.
- **In a terminal a title beats a signature, which beats weak signs together.** Copilot CLI prints "❯ 1. Yes" and "● … (shell)", Claude Code's weak pair; its own title or "tell Copilot what to do differently" must win. The cost: a terminal titled after another tool ("gemini") that runs Claude Code is now that tool. Rare, and the tab title is set by the tool.
- **A chat with no labels and no message sections is read whole** for tools whose profile says so (the default, for Gemini and Devin, which show no labels), and ignored for Claude (`whenUnlabelled: ignore`), as before. The issue's structural fallback (a short turn with no list is yours) is left for SCR-84, which owns how steps are read.
- **`agentWork` is used for one thing now**: a list under a `todo` heading of the profile (Windsurf's "Planned for 3 steps") is the agent's. Approvals and "ran" lines are data for SCR-85.
- **Bundle ids not checked on a Mac are kept to two**: ChatGPT's app (`com.openai.chat`) and Copilot's (`com.microsoft.copilot`, unverified). The newer ChatGPT app and Devin Desktop are left out until their ids are checked; their sites are matched.
- **`didja profiles --json` returns `{ apps, assistants }`**: nothing in the app or the MCP server reads the old array.

- **The corpus labels what really happened, so the baseline is low on purpose** (SCR-82): ChatGPT, Gemini, Copilot and every agent but Claude Code make no task today, and each scenario stays a miss until SCR-83–SCR-89 fix it. The gate for those issues is recall up, precision not down, and no wrong tick.
- **60 new scenarios, 99 in all**: the issue's "at least 60" read as 60 added on top of SCR-64's 39, so every tool family has several and the earlier cases stay.
- **A tool family per scenario, written in the file** (`family`), not guessed from the app: a Chrome window may be Gemini, Copilot, Devin, claude.ai or a done target. The existing 39 got theirs from their first window (Claude → `claude-app`, a terminal → `claude-code`, Outlook → `email`, WhatsApp and Teams → `messaging`).
- **Message sections only where capture writes them**: the Claude and ChatGPT desktop apps get `⟦Message N⟧`; web chats (chatgpt.com, Gemini, Copilot, Devin) and terminals get none, and the editor agents' panels a `⟦Chat⟧` section like VS Code's terminal one. How capture really writes those panels is to be checked when they are supported (SCR-83).
- **An approved agent command is the agent's, a declined one is yours**: Codex, Gemini CLI, Copilot CLI and Aider running a command after you allow it makes no task; Aider's command you decline, or Cursor's you skip and are handed, is labelled yours.
- **The baseline records one run with Apple's model**; its numbers vary a little run to run (a second run differed by one ask). Wrong asks are listed, not gated: they are questions, never ticks.

- **The troubleshooting report holds codes and counts only** (SCR-79): app names and bundle ids, result codes, line counts, versions, paths and settings, never screen text, window titles or task words, so it can be sent without masking. Engine error messages are included as they are (at most 300 characters each); they come from the engine, not the screen.
- **Didja sends the report nowhere itself.** Email to Didja opens a `mailto:` in the user's own mail app and Open a GitHub Issue opens a filled-in page in the browser, the same pattern as Report a Bug; the user sends either. No new network call.
- **The optional masked sample from the issue is not built yet**: Report a Problem with This Window… already gives a masked reading of one window. Left for a follow-up.
- **What the app knows goes into `meta.app_facts`, and the findings are worked out in the engine**, so `didja doctor` from Terminal says the same as the window, and the rules live in one place.
- **Why reads make no task is counted by the full pass only**, so a window read by both lanes is counted once; tasks made come from `didja quality`'s counts, because the fast lane usually makes them before the full pass sees them.
- **"Moved since you allowed it" compares the app's path with where it was when Accessibility was last seen allowed**: macOS ties the permission to the app, and a copy elsewhere is not trusted. It can only be said once Didja has been allowed at least once.

- **Checklists of boxes count like numbered lists, toggle buttons never do** (SCR-80, a new user's Claude app writes its steps as boxes to tick). The same rules decide (mostly actions, not Claude's own plan), so this widens what is read, not what is kept; a toolbar toggle is an AXCheckBox with the AXToggleButton subrole and is written as a button, so "Good response" or "Sidebar" can't make a list.
- **Newer Claude Code is recognised by its status line, or "●" and "❯" together, not by either alone** (SCR-80). A "❯" prompt theme and "●" in a status tool are common in plain terminals.

- **Tick When Didja Is Sure is the default, for new and existing installs** (SCR-74, the maintainer). An install on Ask Me moves once (`meta.looks_done_sure_once`; the app's own flag the same); one on Accept Automatically keeps it. Ask Me stays available.
- **No "both models say done" signal** (the maintainer): asking two models on every look doubles the time and the memory. The second signs are what done looks like matched there, or a ticked box or notice naming the task, each with the model's "done"; or earned trust.
- **Trust key: site or app · source kind · first verb**, not the page path, which would earn trust too slowly (the maintainer). Trust is 5 yes after the last no within 30 days, so a wrong tick (reopened) or a "not yet" suspends the key until 5 more yes.
- **Trust is a table of answers (`trust_events`), not read from evidence wording**, for the same reason as SCR-73's outcomes: a sentence change must not change what is trusted. Earlier confirmations (SCR-71) are not back-filled; trust starts from this version.
- **A step with something exact to look for never sure-ticks** (SCR-69 already made it wait for your yes in Accept Automatically).
- **The first-time "Didja ticked this for you — Undo" note is not built yet**: the row's "ticked for you" label, its why and Not Done are the undo for now. Left for a follow-up.

- **An unclear list is shown as "checking…" instead of held** (SCR-78, the maintainer's call: speed counts as much as being right). It replaces SCR-70's "no task until the verdict". It is kept honest by not counting it as open, never nudging it, and taking back only what you left open when the verdict is Claude's.
- **"Checking" is a confidence (0.1), like "maybe" (0.2)**, not a new column: no schema step, and the app already reads confidence. Every list judged or clear is 0.3 or more.
- **A tick while checking is taken as "yours" for the whole list**: the verdict is saved with model "you", so neither lane asks the model about that list again. A "Claude's" verdict that arrives in the same moment from the other lane still leaves your tick alone.
- **The verdict goes first in the model lane** already (SCR-76 put list verdicts ahead of criteria, looks and titles), so nothing more was needed for this issue's ordering.

- **The judge server is reached through two named pipes with blocking reads** (SCR-77). Every model call sits inside a synchronous rule, and Bun has no synchronous read of a child's output; named pipes opened by the engine give blocking reads with a deadline and an end-of-file when either side goes. They live in a private temporary folder and are removed once open, so nothing is left on disk.
- **One-shot spawns stay as the fallback, and the one-shot flags run the server's own code**, so a server that cannot start, or an older app binary, changes nothing about what is decided.
- **Shipped although the median was not halved.** Measured, launching the app binary is not where the time goes on the maintainer's Mac (0.49 s → 0.47 s); the server still saves the model's load on the first question (1.08 s → 0.56 s) and keeps Ollama loaded. Left for the maintainer to keep or take out.
- **Ollama is warmed when the local model is first used or changes**, by the lane's next question, not the moment the switch is turned on in Settings: the switch is the engine's setting and the server lives in the model lane.

- **The model lane is a second process running today's full pass, not an async rewrite** (SCR-76). Every model call sits inside a rule (an email read decides whether there is a task at all), and each is a blocking call to the app binary; making them async would have meant rewriting those rules. A separate process gets the same result without changing what any rule decides: the fast lane never waits, and the full pass still does everything. The cost is that both lanes read the same screens; what the fast lane already did is a no-op the second time.
- **The fast lane does only what needs no model**: Claude windows (clear lists, commands), markers, archives, signed requests. Mail and chats are skipped there, because their tasks come from the model; an unclear list is queued for the judge (never "maybe") because a judge exists in the other lane. It starts at the full pass's place, so it never re-reads a day of old screens on first run.
- **Woken by a line on the engine's standard input**, not a watched file: the app already starts the engine, a pipe needs no file in Application Support, and the engine (and its lane) can tell when the app has gone. Writes are non-blocking and ignore a closed pipe, so capture never waits and the app never dies of SIGPIPE.
- **List verdicts moved ahead of criteria and looks; criteria stay ahead of looks** (the issue asked for looks before criteria). Criteria narrow which screens a look may use (SCR-67); asking for looks first could let through a screen that criteria would rule out, and a wrong tick costs more than a slower one. A list judged in a pass is still not shown that pass's screens, as before.
- **One model job at a time, for Ollama too, for now.** Two at a time needs async calls or a judge server; SCR-77 (a long-lived judge) is where that fits.

- **Speed is timed inside the engine's pass, not by capture** (SCR-75). `seen_at` is the observation's own time, so capture's delay is included; `engine_at` and `shown_at` are taken from the pass. `shown_at` is the pass's time plus the clock time spent in it, rather than a second wall-clock reading, so the benchmark's fake clock and tests give exact numbers and live reads the same.
- **A tick's "seen" is the newest observation its evidence points to**; a tick whose evidence has no observation (a chat reply, an email response) falls back to the newest observation the pass read. That can make such a tick look a little faster than it was, never slower.
- **The target is chosen by the path, not by whether a model ran.** A list judged by the model, a tick from a screen the model read, an accepted "looks done" and every "looks done?" are held to 10 s; everything else to 3 s, even when a model read the email first, because the issue's target for email tasks is 3 s. Chat asks promoted after their 10-minute wait are reported apart with no target.
- **The benchmark measures the engine's share only**: each observation is read the moment it is written, and polls follow every 5 s. Capture and the wait for the next pass are in the live numbers. Model costs are fixed medians (Apple 1 s, Ollama 2.5 s, from eval/lists.ts), not the real time of the call, so runs compare.
- **The benchmark now polls every 5 s, not every 30 s**, to match the engine's loop; with no model every count is unchanged.

- **"How Didja is doing" counts from a log of outcomes, recorded from now on** (SCR-73), rather than being worked out from tasks and their evidence. The store did not say whether a tick was Didja's or yours, and reopening erased `done_at`, so wrong ticks could not be found after the fact; reading it from evidence wording would also break whenever a sentence changed. The report says from when it counts, and steps made are counted from the same moment so the numbers compare.
- **Counted per step, per event.** Ticking a checklist counts each step it changed; a task asked "looks done?" in two places counts two asks. "No answer" is asks minus yes and not yet, so it includes asks still waiting and ones settled another way.
- **A tick on a task waiting on "looks done?" is a yes**, whichever button made it; any other tick in the list is "by you". A reopening is a wrong tick only when the step's last outcome was one of Didja's ticks.
- **Groups follow the source kind**: Claude (desktop and web), Claude Code, Email, Chat, Added by you (added and My List), Connected tools. The issue's "terminal" is not a source of tasks; terminal runs show as the "command run" kind of tick.
- **Engine dismissals are not "dismissed by you"**: Claude doing a step itself, a connected tool cancelling an item, and an archived email are left out of that count.
- **The app shows eight columns** (made, ticked for you, asked, yes, not yet, by you, cleared, wrong ticks); the breakdown of ticks by kind is in `didja quality`.

- **Capture's window key is the window's identity, written on each observation** (SCR-72), not recomputed by the engine from the title, so the two can never disagree about a live row. The engine keeps its own copy of the rule only for rows written without a key (tests, the benchmark); both test suites check the same cases. Both sides strip a URL at its first `?` or `#` as text, rather than parsing it, so they agree on odd addresses. Rows from before schema 024 are grouped by app and exact title, as before, and never mixed with keyed rows.
- **The title rule strips only what comes and goes**: leading symbols (spinners, dots), an unread count in brackets at either end, and "— Edited". A title that changes in other ways (a terminal that retitles to the running command) is still a new window.
- **The terminal check "same window, within 5 minutes" still compares app and exact title** (`match.ts`). Loosening it to the key could let output from a different window count as a run; a missed tick there is cheaper.
- **Lines are remembered 10 minutes after they leave the screen, at most 4,000 per window.** Shorter than the engine's 30-minute look back, so a line the differ has forgotten is still in the engine's history when it is reported again. The cost: a command run again on a cleared terminal within 10 minutes does not report its command line again (a missed tick at worst); its new output is still new.
- **`assemble` collapses only streaming, not every repeat**: a line is replaced only by a longer version that starts the next batch of the same section, right after it. Dropping every exact repeat in a section was tried and broke emails that share a section name (their lines are alike), and dropping any earlier prefix could drop a real line ("Done" before "Done with the slides"); scroll-back repeats are stopped in the differ instead.

- **Criteria the model writes are distrusted by default** (SCR-67). Apple's model copied the instructions' examples into every answer (a repo it was never shown, "main -> main" for a visibility change, the conversation's name as an id), so: the instructions give no example phrases; a token must be copied from the step or its kept lines and look like an id; a site keeps only path parts it was shown; and criteria judge only screens at one of their own places, so a copied "Pending" cannot hide a screen elsewhere. Shipped although it does not yet raise the benchmark: it rules nothing out that was found before, and the job, its storage and its eval are what a better model or better instructions need.
- **Criteria are forgotten with the task's kept lines** (when it is done or dismissed): they were written from those lines and can hold an id from them. They are a model's paraphrase, like a model-written title, never screen text kept for its own sake.
- **Editing or clearing criteria by hand is left for later**, as the issue allowed; why shows them.
- **"Where you went next" ranks screens but never qualifies a page on its own** (SCR-66). The maintainer's rule that a page which only shares a task's words is never asked about (the Linear issue about a Supabase change) stays; a page soon after you looked at the source counts only when it shows an id from the task, which a page about something else rarely does. Weighting by time puts the screen nearest to when you read the source first, the issue's "weighted by time". Service names come only from capitalised words in the kept context, minus words that only start a sentence and generic ones (Google, Mail, Settings), so a name in the conversation is not confused with every site.
- **Strong tokens leave out years, amounts and commands.** A four-digit year, a number inside "1,200.00" and anything in backticks (a command is a marker of its own) are not ids; a one- or two-digit number counts only as "#42" or after "pull request", "issue", "order"…, matched as `#42` or in a `/pull/42` address, never as a bare "42".
- **An editor is Claude Code only when its panel's own hints are on screen** (SCR-65, as the issue asked). A file name or a document's words never decide it, because CLAUDE.md and docs about Claude Code are exactly what an editor shows. The cost: if the panel's captured text lacks those hints, its lists are missed; a missed task is cheaper than a list of rules on your list.
- **A step Claude carries out itself is dismissed, not ticked.** It was never yours, so ticking it would credit you with Claude's work and teach nothing; dismissed with a note, it shows in why. An edit carries out only a step whose verb changes something (add, set, update, fix…) and that names the edited file; "Review src/auth.ts" is not done by Claude editing it. The Claude Code rules stay in extract.ts, not in a profile: profiles label chat and email windows from their accessibility outline, and a terminal's text has no outline.
- **The benchmark still counts a task that was taken back as made.** It was on your list for a while, so precision does not hide it.
- **The benchmark's labels are the truth, not the engine's current output** (SCR-64). A scenario the engine gets wrong stays wrong in the table until the engine is fixed, so the baseline shows today's misses (one-step lists, a CLAUDE.md in an editor). Only wrong ticks fail CI: misses and unwanted tasks are the numbers later issues move. With no model, chats and emails make no tasks at all (they need the model), so the CI run measures lists, commands and markers; the model runs are by hand, like `eval/ollama.ts`.
- **A task in the benchmark is matched by words in its title**, not by its exact wording, because the model writes chat and email titles and they vary between runs. A tick before the labelled time counts as wrong, as does ticking a task that must not exist. The engine is polled every half minute of the fake clock, so a tick's delay is measured in half minutes.
- **Capture tells lines apart by section and occurrence, not by text alone** (SCR-63). The key is (section, line, n-th time in that section). A line that appears twice in one new snapshot is still reported once, as before: the engine reads text, not counts. Scrolling an older copy of a line back into view under its own message now reports it again (before, it was hidden if the same words were visible elsewhere); the engine already places a reply by its message time, so an old "Done" before an ask does not tick it (tested), and "Only new" covers back-scrolling.
- **Task keys keep every script, and drop accents** (SCR-62). Letters and digits of any script, NFKD with combining marks removed, so "Café" and "Cafe" are one task and Hebrew points do not split one. An English title's key is unchanged. A title with nothing to key by is kept by its exact wording (the key column is unique, and an empty key matched everything). Old lessons with an empty key are deleted once rather than re-keyed: the title they came from is not kept with them.
- **A command is done when it ran and nothing said it failed** (SCR-61). Output or the next prompt after the command shows it was entered; a failure line before the next prompt, or a prompt showing a non-zero status, means it was not done. The failure list leans wide (any line starting "error"/"Error", any non-zero "N failed"): a missed tick is cheap. Only the same window counts, within 5 minutes, so another tab's output never makes a typed command "run"; a terminal that retitles its window when a command starts reads the new title as a new window, whose first observation holds the command and its output together.
- **Didja drafts the issue; Claude only explains** (SCR-57, as the issue asked). Masking stays inside Didja: the kept lines are masked by Didja, and Claude's words are checked against the case's own unmasked text rather than masked, so the explanation stays readable. A word is refused only if it was on the screen or in the task and is neither a label word, a common word nor the app's name; this can refuse an ordinary word that happened to be on screen, and Claude then words it differently. The NID-style ids and real numbers are refused by the three-digit rule; masked zeros pass.

## Walk the Accessibility tree on a 16 MB stack (2026-11-11)
The walk is recursive and allows 100 levels, which deep web pages reach. Rather than lower the depth (and miss text in Gmail and Outlook on the web) or rewrite the walk as a loop, each read runs on a short-lived thread with a 16 MB stack and the capture queue waits for it. A thread per capture (at most about one a second) costs little.

## Release builds are re-signed by a script, not by changing the project (2026-11-11)
Notarisation needs the hardened runtime and a Developer ID signature, and refuses `get-task-allow`. Changing the project's signing would change the Debug build's signature and cost the Accessibility permission (CLAUDE.md: do not change signing). So `scripts/release.sh` builds Release as it is and re-signs a copy: the engine with `scripts/engine.entitlements` (allow-jit and allow-unsigned-executable-memory, which Bun's JavaScriptCore needs), then the app with no entitlements. It signs by certificate hash because the keychain held two copies of the Apple Development certificate. The notary password is stored by the maintainer with `notarytool store-credentials` under the profile `scrolledaway` and never passes through the agent. Shipped as a disk image with an Applications link; the engine is arm64 only, so Apple silicon only.

## Go to Source finds the line by reading the window again (2026-11-11)
Evidence never keeps screen text, so there is no saved position to jump to. When you ask, the window is read again under capture's rules (exclude list first, no password fields), the line that best matches the task's words is scrolled into view, and nothing read is stored. Tasks keep the app, window title and page address of where they were captured (schema 14). That is the same metadata observations already hold, but it is kept for as long as the task. A tab that is not in front, or a closed window, reopens the page's address in a new tab instead of asking for Automation permission to switch tabs. ## Chat tasks: asks of you; a reply ticks unless it puts it off (2026-11-11)

## States that say done are evidence for "looks done?", not ticks (SCR-68, 2026-11-13)
- A ticked box or a notice that names a task makes a screen a candidate on any site, not only where the task is done (the rule for shared words since SCR-66), because it is a state, not a mention. The bar for "names" is higher than for shared words (an id and a word, or two words and 60% of them), and the looks-done model still decides, so a wrong one costs at most a "Not yet".
- A box that names the task but is not ticked rules the screen out, like a "not yet" phrase in SCR-67: fewer wrong asks; a missed ask is cheap.
- Link targets on pages keep no query, fragment or login part: they can hold tokens, and a PR, issue or deploy is named by its path. They are kept only in a page's main landmark, at most 20, and not on sites a chat or email profile labels, which keep their own rules. The engine strips them before URL and env marker matching and before reading Claude's steps: otherwise a page linking to a URL, or a step whose words are a link, would tick a step or add a marker, which would make ticking looser.
- `AXCreated` and `AXSheetCreated` are not listened to, though the issue named them: web apps post `AXCreated` for every new element, which would mean reading many elements per second, and a new sheet takes focus, which the existing notifications already turn into a capture. `AXSelected`, `AXEnabled` and `AXExpanded` are left for later: the issue's change does not say how they would be written or used.
- A notice is text in the observation like any other line (`⟦Notice: …⟧`), so it expires after 24 hours with the rest; no new kind of storage.

## Terminals: reading in the engine, close variants, and a fallback that only asks (SCR-69, 2026-11-13)
- Terminal text is split into commands in the engine (`terminal.ts`), not written as `⟦Command: …⟧` sections by capture as the issue suggested: the engine already reassembles a terminal from several observations (a command's line and its output often arrive in different ones), so splitting there sees the whole run, and stored text stays as it was. `sectionOf` writes the issue's form for reading.
- Extra flags are allowed when matching a run, because `-u`, `--force-with-lease`, `-v` and the like still do the thing; flags that make a run do nothing (`--dry-run`, `-n`, `--help`, `--check`…) are not, and `-n` is refused even where it means something else (git commit's no-verify): a missed tick is cheap. A flag's value is read as an argument, which can only make a match stricter.
- `commandAtPrompt` keeps its exact rule (its test says "nothing after it"); ticking goes through `commandOutcome`, which now uses `sameCommand`.
- The fallback to "looks done?" waits two hours (the issue's N), and looks back at earlier terminal screens only in the five minutes after a step joins, so a run you made early with a different form is still seen without re-reading every screen on every pass. It is never accepted automatically: the issue says such a step "can still only be suggested", and a command is where a wrong tick is easiest to make.
- Editor terminals need focus: the terminal's text is marked only when its input is the focused element, as the issue asks. Output that arrives after you leave the terminal is not marked, so such a run may be missed, never wrongly ticked.

## Unclear lists wait; "maybe" without a model; the local model judges lists (SCR-70, 2026-11-13)
- An unclear list is held until judged rather than shown and taken back: a list that appears and vanishes a few seconds later is worse than one that appears a few seconds late. The checklist to keep is stored in the pending row, so it is made the moment the verdict comes, even if the window is gone.
- "Maybe" is stored as confidence (0.2, every other list at least 0.3), as the issue asked, so no schema change was needed.
- Plan signals only ever decide "Claude's", and only with no step only you can do; anything mixed is left to the model. A missed list is cheaper than a list of Claude's work in your tasks, but a list that names a dashboard or a person is never dropped by wording.
- The local model may judge lists: on 44 made-up lists it was right on all, with no false "yours", against 42 and one false "yours" for Apple's model. This is the rule in CLAUDE.md ("measures better with no new wrong ticks"), so the job list there now includes it. Titles still use Apple's model only.
- The sample set is 24 yours and 20 Claude's, not exactly half: the extra four are the hard mixed kind (a coding word in a step that is still yours).

- The issue is public, so the form says so and warns about an email address, a long number or a link with a path in the text. It warns rather than refuses: the user wrote it and may mean it.
- In Help, not at the top of the menu: the top holds what is used most, and Report a Problem stays there.

## Suggest a Feature is Report a Bug's form for an idea (SCR-52, 2026-11-13)
- One form with two kinds, not a second window: the same way to GitHub (a filled-in issue the user submits, as in SCR-51), the same public-issue cautions. An idea asks what you would like and what it would help with, and is labelled `enhancement` (GitHub's default label for one).
- Versions are off by default for an idea: they rarely matter to one, and leaving them out puts less in a public issue. The box is there to tick.

## The list's controls on a canvas task (SCR-58, 2026-11-13)
- "All line controls" was read from the list row: its hover buttons (Copy, How it looked, Why, Snooze, Dismiss), its menu (Go to Source, Didja Missed This…, Snooze, Dismiss, Not an Action, Mark Done / Reopen) and its keys. Go to Source, which the issue names and which the list has only in its menu, is also a button on the canvas, since a canvas row has room for it.
- Left out on purpose: Rename (the canvas already has it, on Return), Send to Canvas (it is on one), "tick conversation" and the merge buttons (a canvas holds single tasks, not their conversation), and Fold (a canvas lays its steps out itself).
- The canvas calls the same `TaskActions` the list uses, given to it by the app, so a control does exactly what it does in the list; there is no second copy of any rule.
- The buttons sit beside the text rather than over it as in the list: a canvas row wraps, so covering its end would hide words.

## Ticking a heading on a canvas (SCR-59, 2026-11-13)
- "Under a heading" means the tasks after it up to the next heading, whatever their indent: a canvas heading has no level of its own, and that is how the page reads. Worked out in the engine (`canvasSection`), which owns every rule about tasks; the app only draws the circle from the counts it is given.
- Ticking a heading is the same as ticking each task by hand (`changeByYou`): a user's tick, not Didja's, so it cannot tick anything wrongly on its own and How Didja Is Doing counts it as yours.
- A filled heading circle opens its tasks again, like a ticked task's circle. Dismissed tasks are skipped both ways and left out of the count: you said they were not to-dos.
- A heading with no tasks under it has no circle.
